# Architecture and logic

Module and behavior map, maintained through the targeted cleanup, [follow-up recheck](CLEANUP_RECHECK_2026_10_21.md), [pending-flow recheck](PENDING_FLOW_RECHECK_2026_10_21.md) and [loan-flow review](LOAN_FLOW_REVIEW_2026_10_21.md) on 21 October 2026. The [initial cleanup report](CODE_REFINEMENT_2026_10_21.md) retains its original validation; this is not a claim that every line or device state has been proven correct.

## Ownership and data flow

Theme selection writes `theme_id` and `accent_color` in one atomic SQLite statement and updates both caches only after success. The [accent provider](../src/theme/AccentContext.tsx) keeps the immediate preview, orders queued choices and restores the last committed choice on failure. Restore invalidates obsolete queued choices. The picker and Settings show an accessible error, and a single [feedback component](../src/theme/ThemeSaveFeedback.tsx) beside the unlocked dialog host keeps off-screen failures visible. Background widget refresh waits for queued theme persistence.

Reports' calendar uses at least 44dp day controls. Its dense year matrix remains a visual/scrubbable overview; individual tiny cells/month labels are no longer separate buttons. [HeatmapDayPicker](../src/features/reports/HeatmapDayPicker.tsx) provides searchable full-width day and month actions in one native sheet, with virtualized rows. Future days are excluded; month navigation remains available where the report window supports it. Grid hit testing follows the measured weekday header and scaled matrix labels.

Shared [Text/TextInput](../src/components/Text.tsx) support OS text scaling through 200%. Above the reflow breakpoint, single-line labels wrap instead of shrinking, inputs reserve scaled line/padding/border space, number-pad keys grow, and navigation puts the active label below its icon row. [useFontScale](../src/lib/useFontScale.ts) shares one OS subscription and removes it when unused. This is the implemented policy; visual/TalkBack acceptance at 200% on Android remains a separate device check.

[app/](../app) owns Expo Router routes. [src/features/](../src/features) owns screen presentation; [src/components/](../src/components) provides reusable controls. [src/db/](../src/db) owns persisted records and transactional queries. [src/lib/](../src/lib) owns independent calculations and platform workflows. Themes and widgets have separate directories.

The [root layout](../app/_layout.tsx) initializes application services and providers. Screen loads use [useScreenLoad](../src/lib/useScreenLoad.ts); stale requests must not replace a newer scope. Mutations use database transactions and, where appropriate, [useSaveOnce](../src/lib/useSaveOnce.ts) to prevent repeated submissions. [Client](../src/db/client.ts) serializes database operations; callbacks must use the supplied transaction/exclusive handle rather than reopening the database inside that operation.

Modules do not import each other in a cycle; `npm run check:cycles` (also in CI) fails on one, ignoring `import type` and dynamic `import()`. Lower layers stay free of the notification scheduler: [settings](../src/db/settings.ts) only persists, and [afterCommit](../src/db/afterCommit.ts) adds the reminder refresh (for the privacy toggle, `saveHideSensitiveAmounts`). The client's startup steps and shared types live in small modules ([currencyCache](../src/db/currencyCache.ts), [deletedRetention](../src/db/deletedRetention.ts), [dbTypes](../src/db/dbTypes.ts)), and the read-only category list in [categoryList](../src/db/categoryList.ts), so the client and the alert builder do not depend on the modules that depend on them.

[AppDialog](../src/components/AppDialog.tsx) synchronously consumes each displayed confirmation before invoking its action. Repeated taps and callbacks from replaced or unmounted dialogs cannot run obsolete actions or dismiss a replacement notice. [RuleModal](../src/features/recurring/RuleModal.tsx) shares one mutation lock across direct/confirmed saves, deletion and pause/resume; the confirmation's lifetime is independent of the main submit handler. [Account setup](../src/features/profile/AddAccountModal.tsx) starts with the cached currency and applies an asynchronous default only within the same opening and before an explicit user selection. Resetting a completed/partial form does not launch a second unscoped currency read.

[runAppMaintenance](../src/lib/runAppMaintenance.ts) shares overlapping runs, catches up recurring entries before backup and emits transaction-change events when records were added. Recurring failures are logged; the backup step still runs. This is foreground maintenance, not a guaranteed background scheduler.

Screen freshness skips unchanged focus reads for up to five minutes, scoped to data version, calendar day and load dependencies. An expired cache or a clock moving backwards forces a fresh read instead of extending the cache lifetime.

Activity's filter contract lives in [activityFilter.ts](../src/features/transactions/activityFilter.ts), independent of its popup component. Filtering prepares account/category membership sets and a trimmed label once per invocation. Retired payment-method filter keys are ignored; stored transaction metadata remains compatible. Plan builds account/category maps once per loaded snapshot. Home's spending bars memoize their day/week buckets and reuse one selected-bar lookup. These changes retain ordering, currency, refund and privacy rules.

Draft reference validation lives in [draftReferences.ts](../src/features/add/draftReferences.ts), outside route state orchestration. It checks active selections and all staged/split entries against live reference sets; absent selections remain editable and unused mode fields do not block recovery.

## Add transaction flow

The [Add-flow review](ADD_TRANSACTION_FLOW_REVIEW_2026_10_21.md) covers expenses, income, transfers, friend entries, refunds, staged saves, splits and editing. [Add](../app/add-transaction.tsx) waits for complete initial reference/link/split loading before enabling Save or Add more. Failed initial loads offer Retry; superseded or unfocused loads cannot publish late results. Split editing publishes the whole payment only after its parts have loaded successfully.

Save, Add more and confirmed deletion share a synchronous mutation lock. Save exposes its busy state during duplicate checking as well as persistence, and the committed flag prevents queued taps from replaying a successful write during the completion delay. Editing controls stop accepting ordinary pointer input while busy. Reduced motion skips the success delay. Deletion emits the data-change event after commit and bypasses the discard prompt; a deleted screen cannot navigate or show an undo toast after it unmounts. Failed deletion releases the lock for retry.

The edit baseline includes type, refund status, transfer destination, total expression and split allocations, as well as account/category/date/note and retained payment metadata. Split UI keys do not count as data changes. Unchanged plain edits preserve their exact historical minor-unit amount. Split Done is consumed once, and cancellation clears only its own in-memory session, preventing a later direct Split route from exposing the abandoned payment. Existing recovery preparation, partial-batch retry, currency restrictions and linked-entry write restrictions remain in force. Payment-method controls remain absent; accounts identify where money moves.

## Goals and budgets

The [goals/budgets review](GOALS_BUDGETS_FLOW_REVIEW_2026_10_21.md) covers the dedicated list routes and their Home/Plan entry points. List cards use the same overview sheets as Plan; editing and money actions remain separate steps. Keyed form sessions preserve drafts when the same record refreshes and reset them for a new opening/record. Reservation management returns to the editor's draft after both cancellation and a successful money action.

[useSheetMutation](../src/lib/useSheetMutation.ts) shares one synchronous lock and committed guard across creation/edit/archive/delete actions in a sheet session. It dismisses input, distinguishes a failed write from a failed refresh and prevents late completion from controlling a different screen. Contributions/releases keep corresponding commit guards around their completion stages. Native gestures, keyboard geometry and modal sequencing still require device acceptance.

[Budget category eligibility](../src/features/budgets/budgetCategories.ts) matches the database's family privacy rule, including sensitive archived children. Budget creation validates an active expense category and performs duplicate checking, insertion and result lookup in one transaction. Goal creation includes result lookup in its transaction too. Budget deletion captures its Undo snapshot atomically; missing budget edits fail explicitly. Archived manual goals cannot change progress until unarchived; archived reservation releases/moves retain their separate rules.

[Budget aggregate scope](../src/lib/budgetScope.ts) counts parent-covered subcategory budgets once without removing their individual limits or warnings. Spending lookups accumulate signed category/refund totals once into maps. Budget overview recent entries use the ledger's spending-only filter before LIMIT. The shared [local-day hook](../src/features/budgets/useToday.ts) uses one native subscription/timer across rows/screens, suspends its timer in the background and refreshes on resume, including a missed background event.

Goal list loading only fetches data. Completion letters wait for visible savings and no competing sheet, and both list and contribution reveals mark them read on acknowledgement. A failed acknowledgement can retry or close without repeating the financial write; dismissing a failed automatic reveal defers letters for that screen visit. Completion while hidden defers the sealed letter. Reveals also respect a later privacy change. Unavailable linked accounts remain identifiable for editing but cannot launch a transfer. Goal totals describe per-goal progress; existing warnings for duplicate followed accounts and monthly-commitment deduplication remain in place. The stored schema, manual contribution semantics and previous-month rollover policy are unchanged.

## Loan flow

The [loan-flow review](LOAN_FLOW_REVIEW_2026_10_21.md) traces Loans, Home's direct payment links, Plan Debt/Upcoming, notification/widget entry points and Activity's linked-payment undo. The Loans route consumes each detail/payment parameter after a successful list load; later requests work in the same mounted route. Missing loans explain the unavailable link, closed loans open for review, and an empty list shows its setup prompt without a false paid-off summary.

Loan detail sessions are keyed by loan ID. Opening payment captures the installment, account and filing category until the confirmation closes, including the final EMI; refreshing the schedule does not switch the confirmation to the next installment. Actual payment/receipt dates default to the local device day and can be changed to an earlier day. Future dates are blocked by the picker and submit guard. A failed save retains the date and allows retry. Committed saves and undo operations report refresh errors separately; an unmounted sheet does not issue late UI feedback/navigation. The shared button supplies the success haptic once, and reduced motion skips the completion delay.

Borrowed payments and lent receipts retain their expense/income ledger semantics and use the corresponding account wording and balance preview. Non-closed defaulted loans retain payment access, consistent with existing list actions and database recording. Rate/account/asset/prepayment sheets retain existing write guards and child-return behavior. Hidden borrowed-only assets and irrelevant disbursement fees do not affect a lent/existing-loan submission. Untouched setup dates refresh on reopening; explicitly chosen dates remain part of the draft. Rate-date selection respects the loan start date. An asset label can be removed before an estimate exists, and changed prepayment amounts clear the older preview while recalculating.

Payoff dates are available only when the final pending row clears principal. Loans and Plan require every outstanding borrowed loan to have a known payoff before announcing an aggregate debt-free date. Missing/truncated schedules remain visible as incomplete while any available unpaid installment stays recordable; schedule rows distinguish actual paid/received dates from paid-before-tracking history. Plan's lent-only state offers repayment review instead of claiming no loans exist. No amortization formula, persisted money schema or existing loan deletion/undo restriction is changed by this review.

## Preference loading and privacy

Startup awaits the saved sensitive-amount preference before mounting financial screens; a read failure keeps the startup error/retry path. Privacy and theme providers invalidate older asynchronous reads when the user changes a preference, settings are restored, or the provider unmounts. Revealing masked amounts with app lock enabled shares one unlock attempt; a restore that overtakes that attempt invalidates its result. The existing category-based masking scope and session behavior on persistence failure are unchanged.

Saving the privacy preference or changing a category's sensitivity/parent refreshes optional bill/refund reminder content after the database commit. Adding/deleting/restoring a sensitive family member also refreshes the family's existing reminder payloads. Privacy refresh runs even when both topics are now disabled, so stale OS payloads are replaced or cancelled. A scheduling failure does not undo the saved change: category actions and the toggle warn that queued details may remain. A preference-write failure keeps the session switch usable and explicitly reports that persisted settings and queued reminders were not updated. Budgets omit an entire sensitive family, including archived children, from current/lapsed rows and derived rollover figures while privacy is enabled.

Spending alerts store structured budget/category provenance in the existing settings JSON. [Queued spending alerts](../src/db/queuedSpendAlerts.ts) rebuild their copy from live data before scheduling, apply current category-family privacy (including archived members), and discard legacy copy with no provenance when privacy is enabled. Alerts discarded by this check do not return on reveal. Queue reconciliation replaces only unchanged snapshot entries, preserving alerts added or replaced during scheduling. Failed scheduling still reports failure separately from a committed preference or category write.

Recurring and Plan load archived category metadata for privacy classification; absent required category/parent metadata is treated as private. Picker eligibility is separate: new rules/budgets omit archived categories, while an existing rule can retain its archived category and parent. Category archive preserves recurring rules and their automatic posting behavior; the confirmation names that policy. Category archive/restore refresh reminder eligibility after commit. Account archive pauses attached rules and refreshes the notification schedule. Person receipts and transaction-backed person delete/restore/Undo refresh conditional logging reminders; balance-only adjustments do not.

Home Upcoming, Plan due-soon/runway inputs, and Recurring summary/shares/timeline use [one currency scope helper](../src/lib/recurringScope.ts) for the default currency, without conversion. Recurring's individual rows keep their own account currency and explain when other currencies are outside the summary. Subscription pattern detection, rule suppression and new dismissal keys distinguish category/currency pairs; suggestion and Needs you rows carry their currency into visible and spoken amounts. Older category-only dismissal keys continue to cover all denominations and can be brought back through Needs you. Plan passes the stored recurring `anchorDay` through its forecast input so February-clamped occurrences return to their original month-day.

Category creation, reactivation and deletion Undo validate active sibling/root name uniqueness within their write transaction. An implicit parent reactivation is validated too; any collision rolls back the whole action, including captured budgets, and identifies the rename needed before retry. Existing histories and IDs are never merged automatically. See [19 October re-audit fixes](REAUDIT_FIXES_2026_10_19.md) for the seven-finding checklist and current validation.

Category deletion captures the family's monthly budgets alongside its categories; Undo restores all rows atomically in foreign-key order. Built-in categories cannot be reparented, and parent archive/delete checks protect system children in older/restored data. Annual bill edits validate the linked preparation account's currency inside the rule-update transaction. Tracked refund receipts preserve purchase labels; exact generated legacy labels are repaired at startup/restore, while manually linked or custom text is preserved. Every new receipt refreshes notifications once after commit, including backdated receipts. See [19 October audit fixes](AUDIT_FIXES_2026_10_19.md) for regression evidence.

## Current flow audit corrections

Draft persistence flushes pending clears as well as filled forms, suspends automatic writes while a recovery candidate awaits a decision, and resumes after a failed navigation discard. Resume validates references for the active entry type and actual staged/split content, ignoring unused selections from earlier modes. Recovery reads are invalidated when save preparation starts. New-entry/split saves remove and suspend the recovery copy before financial writes; preparation failure leaves the form and ledger unchanged. A failed batch retains only unsaved entries and restarts recovery from that remainder; staged batches retain their existing partial-save contract rather than becoming atomic.

Future-date confirmations inspect the dates of the rows actually being saved. A successful split write remains successful if its optional highlight lookup fails. Refunds retain Log today but omit Make recurring because recurring rules cannot represent refunds. Refund updates distinguish committed changes from subsequent refresh failures, clear old receipt input after a successful write, and keep input after actual write failure. Add completion checks its mount lifetime before success feedback or delayed Back navigation, and emits transaction-change events after successful or partially successful writes.
