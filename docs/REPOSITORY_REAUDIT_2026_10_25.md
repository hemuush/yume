# Repository re-audit — 25 October 2026

This pass extends the [app-flow audit](FULL_APP_AUDIT_2026_10_25.md) and its nine reproduced fixes. It uses the Ponytail skill and the exact [Expo SDK 58 documentation](https://docs.expo.dev/versions/v58.0.0/), preserving the existing visual design and financial product rules.

## Coverage method

The [per-file inventory](REPOSITORY_REAUDIT_COVERAGE_2026_10_25.csv) records every tracked or nonignored first-party file, byte count, SHA-256 and check category. Every file's complete contents were read by the inventory checks. Source files also received syntax/import and repository static checks; tests were exercised by the runners below. Manual inspection traced the routes and boundaries listed in the app-flow audit, with additional checks of dependency/configuration ownership, native plugins, exports, locks, file inputs and shared motion.

This distinguishes automated full-file coverage from manual review: it does **not** claim that a human-equivalent line-by-line review of every source/test line or every possible device state occurred. Generated native projects, node_modules, ignored build outputs, local attachments and the separate design-preview/site workspaces are outside the first-party inventory. Binary assets were inspected for references and signatures rather than interpreted as code. The inventory itself has no self-hash.

The inventory contains **1,042 files**: 907 TypeScript/JavaScript files (including 368 test files across the runners), 7 JSON configuration/lockfiles, 24 PNG assets, 87 Markdown documents and 17 other metadata/native/generator/coverage files. Both Python generators also passed AST parsing. All PNG assets have valid signatures/dimensions and full-path references in source/config/generators. No case-colliding paths or matches for the checked secret/key patterns were found; that scan is not proof that arbitrary secrets cannot exist.

All 28 route/layout modules and the separate JavaScript widget registration are included as entry points. The app-flow audit records their navigation, loading, mutation, privacy, currency and recovery contracts. Tests and performance fixtures remain separate graph roots; files used only by build/native/generation tooling are not deleted for lacking an app import. The final graph found no unreachable production-module candidate under these entry points; this is not an unused-export guarantee.

## Structure and dependencies

The maintained backup guide now identifies format 6 as the current export format and format 4 as the earlier introduction of planner data. The data model distinguishes the existing goal_activity journal from account transactions; manual goal changes do have history. Expense-label validation is explicitly marked as its original implementation run. The build guide now separates current commands/configuration from signing history and CI queueing from a finished remote APK.

Routes remain in app/, shared controls in src/components, domain UI in src/features, persistence in src/db and independent calculations/platform operations in src/lib. Components use PascalCase; ordinary hooks/helpers use their existing descriptive names; styles stay feature-local. No broad moves or cosmetic renames were needed. The larger route/query modules were reviewed through their callers and tests; splitting them purely for a line-count target would add churn without fixing behavior.

The installed tree has no invalid or missing top-level packages. Expo's compatibility check accepts the installed versions. Newer versions exist for React/test-renderer, the widget library, keyboard controller, view-shot and TypeScript; none was blindly substituted for the SDK-compatible set. No dependency, lockfile, native API or database schema change was introduced.

The runtime/source scan found no network request or dynamic-code evaluation API in app/src. Native permissions, capture gating, widget-provider authorization, route allowlists, SQL bindings, restore rollback and export escaping were inspected with the existing security checks. [SECURITY.md](../SECURITY.md) documents the implemented controls and limits. The documented CLI-only node-forge exception remains; this is not a zero-advisory claim.
