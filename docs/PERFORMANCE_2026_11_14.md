# Performance with a large ledger (14 November 2026)

Measured first, then changed only where the measurement pointed. Every change keeps what the screens show exactly the same, and the proof for that is a test or a before-and-after comparison, never a belief. Nothing here was run on a phone: desktop timings stand in for one (a phone is about 5 to 10 times slower), and the UI numbers below were taken with the CPU slowed 6 times in the browser render.

## How it was measured

- **Database reads, real SQLite.** `PERF=1 PERF_ENTRIES=100000 npx jest src/perf/loadPerf.test.ts` times what each screen loads and counts its database round-trips (on the phone every one waits its turn in a single queue, so the count matters as much as the time). It now also lists the slowest SQL statements. `src/perf/slowStatements.test.ts` (same switches) times each loader on its own and prints the query plan of its slowest statements: a `SCAN` of the transactions table, or an index that does not narrow the rows, is what to look for. The ledger is `src/perf/seedLedger.ts`: 20,000 entries by default over three years, seven accounts, loans, budgets, goals, rules and people; 100,000 and 300,000 were used for scaling.
- **Proving nothing changed.** `PERF=1 PARITY_OUT=<file> npx jest src/perf/outputParity.test.ts` writes 279 figures every screen reads. Run on the original code and the new code back to back and compare the two files: they are identical at 20,000 and 100,000 entries (one figure, the monthly-pattern list, varies between two runs of the same original code at 100,000 entries, because entries of one day are ordered by an insertion-second timestamp; it is not touched here).
- **Screens with a large ledger.** The browser render was run with 30,000 extra entries (Activity, Home, Reports and Plan), with React's profiler and a CPU profile, and with the CPU slowed 6 times. First render of Home and Reports costs the same with 1 or 30,000 extra entries: the lists are windowed and the figures come from aggregate queries, so those screens do not slow down as the ledger grows.

## What scaled badly, and what changed

| Where                                          | Before                                                                                                                                                                           | After                                                                                                                                           |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Reports' cash-flow bars (`getMonthlyCashFlow`) | Summed the whole ledger to draw 7 months: 11 ms at 20,000 entries, 51 ms at 100,000, growing with every entry                                                                    | Sums only the months shown; the first month with data (which marks earlier months "not recorded") is a separate cheap lookup: 2 ms and 9 ms     |
| Reports load                                   | 62 ms / 191 ms (20,000 / 100,000 entries)                                                                                                                                        | 44 ms / 141 ms                                                                                                                                  |
| Activity: switching Week / Month               | The screen rendered 5 times and every visible day about 4 times (28 day renders for a Month switch, 36 for a Week switch); React commits about 320 ms (6 times slower: far more) | 1 and 5 day renders; commits about 65 ms                                                                                                        |
| Activity: deleting or undoing one entry        | All 7 visible days redrew                                                                                                                                                        | 1 day redraws                                                                                                                                   |
| Activity: a closed group of entries            | Built every sub-row and formatted every amount on every render, open or not (71 ms in one Month switch)                                                                          | Builds them only while the group is open or being touched (24 ms)                                                                               |
| Date labels (every day heading, chart label)   | A new `Intl` formatter for every label                                                                                                                                           | One formatter per label, made on first use, and the labels of dates already shown are kept; identical text for every day of four years         |

Why Activity redrew so much: a reload stored a new empty list of notes (a state change that rebuilt every day's entry list), a new `reorderDay` function whenever the period changed, and accounts that carry a balance which moves with every entry (so anything built around them changed after each edit). Now a reload that found nothing new changes nothing held by the screen (`keepIfEqual`, `reuseUnchanged`), the days read only the names, currencies and sets they use (kept the same object while their content is), `reorderDay` reads the period when called, and a day skips redrawing when its entries are the same objects (`sameElements`).

## Tests that keep it this way

- `src/perf/bulkData.test.ts` runs in every test run on a 20,000-entry ledger: figures equal a recomputation from the raw rows (period totals, cash flow for 7, 12 and 30 months with and without private categories, every account's balance), and each screen's load stays within its round-trips (Home 60, Activity 18, Reports 62, Plan 8; today 52, 15, 52, 5) and a generous time.
- `src/db/cashFlowRecorded.test.ts` pins which months count as recorded, including an empty stretch after the first entry (the case that a window alone would get wrong).
- `src/features/transactions/sameObjects.test.tsx` and the day test in `TimelineDay.test.tsx` pin the identity rules and that a day still redraws when an entry changes; `dateLabels.bulk.test.ts` pins the labels against `toLocaleDateString`.

## Left alone, on purpose

- **Whole-history sums** (a month's carry-in, every account's balance, net worth): inherent to deriving a balance from entries, already served by covering indexes. At 100,000 entries each is 15 to 35 ms on a desktop. A stored running balance would remove that cost and add a way for a balance to drift from its entries, which is not a trade worth making for a money app without a device showing the need.
- **Home's and Reports' first render** commits several times (7 and 6) after the data arrives. The cost does not grow with the ledger. Reducing it means untangling each screen's loading effects, which is its own careful change.
- **The Needs-you card** reads 38 statements; it is the heaviest part of Home's load (about 130 ms at 100,000 entries, a desktop). Its monthly-pattern lookup is already limited to the last 7 months.
- **Not done on a phone.** The real test is a mid-range Android phone with a large ledger; none was available.
